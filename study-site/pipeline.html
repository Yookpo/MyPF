3 · GPU 내부

    Rendering Pipeline

    이 페이지의 질문 DX11 파이프라인의 각 단계는 MyPF의 어느 줄에서 설정되고, 어느 셰이더 줄에서 쓰이는가?

    학습 목표

    이 페이지를 마치면 다음을 할 수 있다.

    1. IA · VS · RS · PS · OM 각 단계의 입력과 출력을 MyPF의 실제 데이터(큐브 24정점, HDR 타깃 등)로 말한다
    2. 각 단계를 만드는 줄(Initialize), 거는 줄(Draw 직전), 쓰는 줄(HLSL)을 짚는다
    3. 같은 단계가 씬 패스와 전체 화면 패스에서 어떻게 다르게 쓰이는지 설명한다
    4. CPU 구조체 ↔ InputLayout ↔ HLSL 구조체, CPU 상수 데이터 ↔ cbuffer를 바이트 단위로 대조한다
    5. 행렬 전치 규약과 색공간 변환이 각각 어느 단계, 어느 줄에서 일어나는지 설명한다

    파이프라인 지도

    전체 화면 패스는 정점 버퍼 없이 그린다. 그러면 IA 단계에서는 무엇을 설정하는가?

    MyPF가 쓰는 단계는 IA · VS · RS · PS · OM 다섯이다. 테셀레이션(HS · DS)과 GS는 쓰지 않는다. 아래 두 줄은 각 단계에 무엇이 걸리는지를 씬 패스와 전체 화면 패스로 나눠 보여 준다. 열을 누르면 그 단계 설명으로 이동한다.

    셰이더 8개는 모두 런타임에 컴파일된다

    Renderer::Initialize가 D3D11Utils를 거쳐 D3DCompileFromFile로 컴파일한다(진입점 main, vs_5_0 / ps_5_0, D3D11Utils.cpp:124, 167, 198). 경로가 Shaders\… 상대 경로라 작업 디렉터리가 MyPF/여야 한다.

    행렬이 CPU에서 셰이더로 가는 길

    1. CPU 행렬 MSimpleMath, 행벡터 규약 (v · M)
    2. Transpose() 후 업로드메모리에 Mᵀ Renderer.cpp:597
    3. HLSL 기본 column_major열 단위로 읽어 다시 M
    4. mul(pos, model)행벡터 × M simpleVertexShader.hlsl:14

    법선용 invTranspose는 반대로 전치하지 않고 M⁻¹을 올린다(Renderer.cpp:599-601). 셰이더는 그것을 (M⁻¹)ᵀ로 읽고, w = 0인 법선에 곱한 뒤 .xyz만 쓴다(simpleVertexShader.hlsl:24-25). 행벡터 규약에서 법선 변환 행렬은 (M⁻¹)ᵀ이므로 결과가 맞다. 중간의 Translation(Vector3(0))은 이미 전치된 행렬의 4행을 0으로 만드는데, 그 자리는 원래 0이라 아무 일도 하지 않는다.

    보간을 거치면 법선 길이가 1보다 짧아진다. 그래서 VS에서 정규화하고(simpleVertexShader.hlsl:26) PS에서 한 번 더 정규화한다(simplePixelShader.hlsl:24).

    전체 화면 삼각형

    컬링과 정점 감기 방향

    FrontCounterClockwise = false라서 화면에서 시계 방향으로 감긴 삼각형이 앞면이다. greybox 큐브는 여섯 면 모두 바깥에서 볼 때 시계 방향으로 정점이 놓여 있다 (GeometryGenerator.cpp:59-163, 178-185). 그런데 CullMode가 NONE이라 뒷면도 그려진다.

    뒷면을 그리기 때문에 PS가 표면 뒤에서 보는 픽셀도 계산한다. 이때 빛 방향 L이 시선 V의 정반대가 되면 하프 벡터 L + V가 0이 되어 normalize가 NaN을 만든다. ComputeDirectLighting이 그 길이를 따로 검사하는 이유다(Lighting.hlsli:128-133).

    Renderer::SetViewPort는 m_screenViewport 멤버를 덮어쓴다. 후처리에서 이 함수를 쓰면 복원할 화면 뷰포트가 사라지므로, Bloom 구간은 지역 D3D11_VIEWPORT를 쓴다(Renderer.cpp:499-506).

    확인 코드에서 바로 찾을 수 있는 것

    Vertex 한 개는 몇 바이트이고, TEXCOORD는 몇 번째 바이트에서 시작하는가?

    정답과 근거

    44바이트, 36번째 바이트부터. Vector3 세 개(12 × 3) + Vector2 하나(8)이고, InputLayout의 TEXCOORD 오프셋이 4 * 3 * 3이다(Renderer.cpp:154).

    LightConstantData의 크기를 바이트로 계산하라.

    정답과 근거

    432바이트 = 16바이트 레지스터 27개. 머리 3개 + PointLightConstantData(48B, 3개) × 8(ShaderConstants.h:26-47). 16의 배수라 static_assert를 통과한다.

    추론 코드를 따라가 결론을 내야 하는 것

    정점 COLOR는 최종 색에 쓰이지 않는다. InputLayout에서 COLOR 항목만 지우면 무슨 일이 생기나?

    정답과 근거

    VS_INPUT에 COLOR0가 남아 있으므로 VS 입력 시그니처를 만족하지 못해 CreateInputLayout이 실패한다(D3D11Utils.cpp:142). Renderer::Initialize가 false를 반환해 앱이 시작되지 않는다.

    model 행렬을 전치하지 않고 올리면 셰이더 결과는 어떻게 되는가?

    정답과 근거

    셰이더가 Mᵀ를 쓰게 된다. 행벡터 v에 Mᵀ를 곱하면 x · y · z에는 M의 3×3 부분이 전치된 채 적용되고(순수 회전이면 반대 방향 회전), M의 4행에 있던 이동 성분은 x · y · z가 아니라 w로 들어간다. 이동이 사라지고 w가 바뀌어 원근 나눗셈 결과도 달라진다.

    전체 화면을 사각형(삼각형 2개) 대신 큰 삼각형 하나로 덮는 이유는?

    정답과 근거

    정점이 3개뿐이라 정점 버퍼 없이 SV_VertexID와 상수 배열로 만들 수 있고(fullscreenVertexShader.hlsl:8, 14), 화면 밖으로 나간 부분은 RS 클리핑이 버린다. 그래서 IA에는 InputLayout을 null로 두고 Draw(3, 0)만 부른다(Renderer.cpp:408, 414).

    후처리 패스는 깊이 테스트를 하는가? DepthStencil State는 그대로 LESS다.

    정답과 근거

    하지 않는다. DrawFullScreenPass가 DSV 자리에 nullptr를 건다(Renderer.cpp:403). 깊이 버퍼가 없으면 깊이 테스트와 기록이 일어나지 않는다. State 객체는 남아 있어도 쓸 대상이 없다.

    Debug View를 Bright로 두면 Final보다 색이 거칠고 밝은 곳이 하얗게 날아간다. 어느 단계의 차이 때문인가?

    실험 실행해서 확인할 것

    RenderDoc에서 씬 DrawIndexed 하나를 고르고 Mesh Viewer의 VS Input / VS Output을 보라. 정점 수, 인덱스 수, SV_POSITION의 w는 어떤 값인가?

    정점 24개, 인덱스 36개(GeometryGenerator.cpp:178-185). w는 투영 행렬이 뷰 공간 z를 옮겨 둔 값이라 카메라에서 멀수록 크다.

    예상과 근거

    예상: 바깥 면은 그대로 보인다. 큐브의 여섯 면 모두 바깥에서 볼 때 시계 방향이고 FrontCounterClockwise = false이기 때문이다(GeometryGenerator.cpp:59-185, Renderer.cpp:766). 카메라가 상자 안에 들어가면 그 상자의 안쪽 면이 사라진다. 실제로 확인한 뒤 결과를 기록해 둘 것.

    Play 모드에서 전원을 켜고 네온이 모두 켜진 뒤 캡처하라. Texture Viewer에서 HDR 씬 타깃의 네온 픽셀 값은 1을 넘는가? 같은 위치의 백버퍼 값은?

    확인 포인트

    네온의 emissive 세기는 7~18이다(AppBase.cpp:380, 395, 410). 다만 시퀀스가 켜기 전에는 emissive 배율이 0이라(PointLightSequence.cpp:85) 전원을 켠 뒤에 봐야 한다. 백버퍼 값은 톤 매핑을 거쳐 0~1 범위다.

    문서와 다른 점

    • 문서와 다름 DirectionalLight.h:11 주석은 "셰이더가 normalize하지 않으므로"라고 하지만, 실제로는 GPU(Lighting.hlsli:69)와 CPU(Renderer.cpp:344) 양쪽에서 정규화한다. AGENTS.md의 "그 함수 한 곳에서만"은 부호 반전에 대해서만 맞다.
    • 문서와 다름 AGENTS.md는 PS b0 재바인딩을 지우면 "두 번째 프레임부터 조명이 사라진다"고 적었다. 현재 코드에서는 첫 프레임부터 Light가 걸리지 않는다(위 추론 질문 참고).
    • 문서 보충 AGENTS.md §7은 invTranspose의 결과가 "우연히 맞다"고 적었다. 코드를 따라가면 Translation(0)만 효과가 없고, 결과가 맞는 것은 전치 두 번과 w = 0 때문이다(VS 섹션).
    • Ambient 항은 조명 색을 쓰지 않는다: albedo * ambientStrength(simplePixelShader.hlsl:48).
